# Migrasi SQLite — fondasi eksperimental, belum untuk deployment

**Status:** belum tersedia sebagai pilihan database saat startup. Aplikasi masih menggunakan PostgreSQL dan fallback RAM yang sudah ada; tidak ada perubahan default. Jangan mengonfigurasi Wispbyte untuk SQLite berdasarkan kode ini atau menganggap tahap 8 selesai. Jangan gunakan backend SQLite eksperimental untuk data produksi.

Fondasi awal `src/services/storage/sqlite.js` menggunakan `node:sqlite`, file SQLite, WAL, foreign keys, busy timeout dan transaksi `BEGIN IMMEDIATE` sinkron dengan rollback. Callback transaksi harus sinkron dan tidak boleh melakukan panggilan jaringan, Discord, provider, atau I/O eksternal. `DatabaseSync` memblokir event loop selama query atau busy timeout: batasi ukuran dan durasi transaksi; ini bukan bukti aman untuk beban produksi Wispbyte.

Adaptasi **belum tersambung ke startup**: uji lokal memakai adapter eksplisit; API penyimpanan AI foundation/welcome/chat/knowledge/Activities dan transaksi ekonomi mengenali adapter tersebut. Poin Activities masih terpisah dan belum terhubung ke wallet.

Perkembangan eksperimental: adapter API key-value bot mencakup CRUD, TTL untuk key temp/cache, alias key lama, daftar key dan increment/decrement atomik; data bot dipisahkan dari namespace AI. Skema SQLite internal versi 1 dan 2 dapat naik ke versi 3 secara transaksional, dan tabel yang hilang/versi tidak dikenal ditolak. Dashboard welcome, pengaturan modul, kasus, tiket, leaderboard dan edit anggota memiliki jalur SQLite yang diuji lokal. Pada SQLite, pembelian role premium, wipe data pengguna, dan penghapusan sistem tiket **ditolak sebelum tindakan** sampai dapat dipindahkan dengan aman. Counter tiket menggunakan increment atomik. SQLite menolak penulisan saldo gaya lama; edit dashboard saldo memakai transaksi yang sama dengan akun ekonomi.

Ini belum berarti kompatibilitas bot selesai. Semantik key terstruktur PostgreSQL yang mentransformasi data belum semua disamakan dan diuji; legacy data PostgreSQL belum diimpor. `list()` adapter saat ini memindai maksimal 10.000 key dan 10.000 akun, kemudian gagal tertutup, bukan strategi final untuk beban besar. Penulisan konfigurasi bot lain yang masih read-modify-write dapat menimpa perubahan dashboard. Jalur giveaways, seluruh operasi dashboard/bot, scheduler, izin, kegagalan, penghapusan, backup dan restore masih perlu audit dan uji terintegrasi. Implementasi PostgreSQL untuk pembelian role dan wipe juga masih mempunyai risiko writer lama. Contoh pilihan path tidak disediakan sebagai konfigurasi deployment karena belum lengkap.

Tes fondasi menggunakan file sementara dan proses terpisah, bukan mock SQLite: jalankan `node --test tests/sqlite-{foundation,bot-database,dashboard}.test.js` dengan Node 22.13+ (diverifikasi dengan 22.23.5). `node:sqlite` masih dapat memberi peringatan eksperimental. Suite lama `node --test tests/tahap{5,6,7,8}*.test.js` juga harus lulus.

Sebelum beralih: audit seluruh jalur baca/tulis dan transaksi termasuk role premium dan penghapusan; lengkapi migrasi versi skema, driver/API serta pengecekan versi dan kegagalan startup tanpa fallback RAM; tes kompetisi lintas proses, restart, rollback, data lama dan seluruh fitur; pastikan satu lokasi file persisten dengan izin terbatas; pastikan backup konsisten menggunakan SQLite backup API atau snapshot yang aman dengan database berhenti, termasuk WAL, dan uji restore. Mengopi file `.db` saja saat WAL aktif bisa menghasilkan backup tidak konsisten. Verifikasi kapasitas, latensi, filesystem dan persistensi Wispbyte saat tahap 9.

PostgreSQL ke SQLite **tidak otomatis dimigrasikan**. Bila ada data PostgreSQL, hentikan semua writer, buat dan verifikasi backup, gunakan prosedur ekspor/impor teruji yang mencakup seluruh tabel, key legacy, TTL dan relasi, bandingkan data dan uji restore sebelum cutover. Belum ada skrip migrasi yang aman untuk digunakan. Jangan menjalankan bot dengan dua backend aktif pada data sama; jangan menyatukan reward sampai semua writer ekonomi memakai transaksi yang sama.
