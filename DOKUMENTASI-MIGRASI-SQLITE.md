# Migrasi SQLite — fondasi eksperimental, belum untuk deployment

**Status:** belum tersedia sebagai pilihan database saat startup. Aplikasi masih menggunakan PostgreSQL dan fallback RAM yang sudah ada; tidak ada perubahan default. Jika ada permintaan SQLite eksplisit (`DATABASE_ENGINE`, `DATABASE_DRIVER`, atau `DB_TYPE` bernilai `sqlite`, `DATABASE_URL` berawalan `sqlite:`/`file:`, atau `DATABASE_PATH` terisi), startup kini berhenti dengan `SQLITE_INCOMPLETE` sebelum mencoba PostgreSQL atau fallback RAM. Ini adalah pengaman, bukan cara mengaktifkan SQLite. Jangan mengonfigurasi Wispbyte untuk SQLite berdasarkan kode ini atau menganggap tahap 8 selesai. Jangan gunakan backend SQLite eksperimental untuk data produksi.

Fondasi awal `src/services/storage/sqlite.js` menggunakan `node:sqlite`, file SQLite, WAL, foreign keys, busy timeout dan transaksi `BEGIN IMMEDIATE` sinkron dengan rollback. Callback transaksi harus sinkron dan tidak boleh melakukan panggilan jaringan, Discord, provider, atau I/O eksternal. `DatabaseSync` memblokir event loop selama query atau busy timeout: batasi ukuran dan durasi transaksi; ini bukan bukti aman untuk beban produksi Wispbyte.

Adaptasi **belum tersambung ke startup**: uji lokal memakai adapter eksplisit; API penyimpanan AI foundation/welcome/chat/knowledge/Activities dan transaksi ekonomi mengenali adapter tersebut. Poin Activities masih terpisah dan belum terhubung ke wallet.

Perkembangan eksperimental: adapter API key-value bot mencakup CRUD, TTL untuk key temp/cache, alias key lama, daftar key dan increment/decrement atomik; data bot dipisahkan dari namespace AI. Skema SQLite internal versi 1–3 dapat naik ke versi 4 secara transaksional, dan tabel yang hilang/versi tidak dikenal ditolak. Dashboard welcome, pengaturan modul, kasus, tiket, leaderboard dan edit anggota memiliki jalur SQLite yang diuji lokal. Pada SQLite, pembelian role premium, wipe data pengguna, dan penghapusan sistem tiket **ditolak sebelum tindakan** sampai dapat dipindahkan dengan aman. Counter tiket menggunakan increment atomik. Pembersihan TTL tersedia secara bounded dan transaksional di adapter, tetapi belum terhubung ke scheduler dan belum mengatasi pertumbuhan WAL atau kebutuhan vacuum. Audit verifikasi pada adapter SQLite disimpan di tabel terpisah, tanpa fallback diam-diam ke PostgreSQL. SQLite menolak penulisan saldo gaya lama; edit dashboard saldo memakai transaksi yang sama dengan akun ekonomi.

Ini belum berarti kompatibilitas bot selesai. Semantik key terstruktur PostgreSQL yang mentransformasi data belum semua disamakan dan diuji; legacy data PostgreSQL belum diimpor. `list()` adapter kini membatasi pencarian ke prefix guild yang dikenali dan alias lamanya; panggilan tanpa prefix tetap dapat memindai seluruh database. Lebih dari 10.000 key/akun yang cocok akan gagal tertutup. Query prefix dan beban besar masih memerlukan pengukuran serta optimasi sebelum produksi. Alias daftar catatan moderasi kini dipetakan dengan benar; data yang terlanjur dimigrasi oleh kode pemetaan lama perlu diaudit secara terpisah. Pada adapter SQLite, konfigurasi guild dibaca dengan snapshot: full-write harus cocok dengan snapshot dan pembaruan parsial digabungkan secara atomik; penulisan langsung melalui API key-value ditolak. Penggunaan snapshot dan semua call site, termasuk efek Discord sebelum penyimpanan, masih harus diaudit dan diuji. Penulis konfigurasi PostgreSQL yang lama masih punya risiko stale-write. Jalur giveaways, seluruh operasi dashboard/bot, scheduler, izin, kegagalan, penghapusan, backup dan restore masih perlu audit dan uji terintegrasi. Implementasi PostgreSQL untuk pembelian role dan wipe juga masih mempunyai risiko writer lama. Contoh pilihan path tidak disediakan sebagai konfigurasi deployment karena belum lengkap.

Tes fondasi menggunakan file sementara dan proses terpisah, bukan mock SQLite: jalankan `node --test tests/sqlite-*.test.js` dengan Node 22.16+ (diverifikasi dengan 22.23.5; `sqlite.backup` memerlukan 22.16+). `node:sqlite` masih dapat memberi peringatan eksperimental. Suite lama `node --test tests/tahap{5,6,7,8}*.test.js` juga harus lulus.

Sebelum beralih: audit seluruh jalur baca/tulis dan transaksi termasuk role premium dan penghapusan; lengkapi migrasi versi skema, driver/API serta pengecekan versi dan kegagalan startup tanpa fallback RAM; tes kompetisi lintas proses, restart, rollback, data lama dan seluruh fitur; pastikan satu lokasi file persisten dengan izin terbatas; file SQLite baru dibuat dengan mode 0600 dan jalur file symlink ditolak, tetapi izin file yang sudah ada tidak diubah dan direktori induk tetap harus tepercaya; fondasi `backupTo` eksperimental memakai SQLite Online Backup API, membuat file baru tanpa overwrite dengan mode 0600, dan memeriksa `quick_check`; tes lokal memulihkan snapshot saat ada writer. Ini belum terhubung ke skrip operasional: direktori harus tepercaya, akses backup dibatasi, dan prosedur backup/restore serta retensi tetap harus diuji pada lingkungan deployment. Gunakan API backup atau snapshot yang aman dengan database berhenti, termasuk WAL. Mengopi file `.db` saja saat WAL aktif bisa menghasilkan backup tidak konsisten. Verifikasi kapasitas, latensi, filesystem dan persistensi Wispbyte saat tahap 9.

PostgreSQL ke SQLite **tidak otomatis dimigrasikan**. Bila ada data PostgreSQL, hentikan semua writer, buat dan verifikasi backup, gunakan prosedur ekspor/impor teruji yang mencakup seluruh tabel, key legacy, TTL dan relasi, bandingkan data dan uji restore sebelum cutover. Belum ada skrip migrasi yang aman untuk digunakan. Jangan menjalankan bot dengan dua backend aktif pada data sama; jangan menyatukan reward sampai semua writer ekonomi memakai transaksi yang sama.
