# PostgreSQL — status kesiapan hosting

PostgreSQL adalah backend runtime saat ini. Mulai perubahan ini, ketika koneksi atau inisialisasi PostgreSQL gagal, startup berhenti dengan `POSTGRES_UNAVAILABLE`; tidak ada fallback ke database RAM. Ketidakcocokan versi skema berhenti dengan `SCHEMA_VERSION_MISMATCH`. Kegagalan pembuatan tabel dasar juga menghentikan inisialisasi. Setelah masalah diperbaiki, restart bot; percobaan koneksi ulang dalam proses yang sama juga tidak lagi terkunci pada kegagalan sebelumnya. SQLite tetap belum bisa dipilih saat startup.

Tes lokal mencakup PostgreSQL 17 pada skema kosong, ketidakcocokan versi, koneksi gagal lalu pulih, inisialisasi bersamaan, kegagalan pembuatan tabel, dan proses bot yang berhenti sebelum web/Discord jika PostgreSQL tidak tersedia. Tes startup juga berjalan pada Node 20 lokal. Ini **bukan** uji deployment Wispbyte, Discord, data pengguna sesungguhnya, koneksi TLS sebenarnya, atau seluruh fitur.

Pengaman ini khusus **startup**. Ketika bot sudah online, endpoint `/ready` kini memeriksa PostgreSQL dengan query aktual, tetapi itu bukan pengaman untuk operasi bot: beberapa jalur PostgreSQL lama masih menangkap error dan mengembalikan nilai default. Pembuatan indeks/trigger masih memiliki jalur yang mencatat error dan melanjutkan; beberapa jalur transaksi fitur dan efek Discord juga masih perlu audit. Jangan menganggap keseluruhan PostgreSQL sudah bebas kehilangan data hanya karena startup berhasil.

Sebelum hosting: siapkan database PostgreSQL terpisah dan persisten untuk setiap pengguna bot, atur koneksi lewat environment dengan rahasia privat, verifikasi aturan koneksi dan TLS provider, serta jalankan tes dari database kosong dan backup/restore di lingkungan deployment. TLS pada runtime dan skrip migrasi Node kini memverifikasi sertifikat dan identitas server; lihat rincian di bawah. Jangan membagikan token, URL database, atau file `.env` di repository atau chat. Prosedur Wispbyte dan backup/restore end-to-end belum terverifikasi.


## TLS PostgreSQL (runtime dan migrasi Node)

Pada `NODE_ENV=production`, TLS aktif secara default dengan verifikasi sertifikat **dan nama host/IP**, termasuk URL yang memakai `sslmode=require`, `verify-ca`, atau `verify-full`. Ketiganya diperlakukan sebagai verifikasi penuh; `verify-ca` tidak mengurangi pemeriksaan nama host. Parameter TLS URL dibaca dan dibersihkan sebelum diberikan ke driver karena parameter URL dapat menimpa objek SSL. Runtime, `scripts/migrate.js`, dan `scripts/migrate-keys.js` menggunakan konfigurasi yang sama.

Jika server memakai CA privat, taruh sertifikat CA yang dipercaya di filesystem yang aman dan atur `POSTGRES_SSL_CA_FILE` ke path file tersebut, atau gunakan `sslrootcert` dalam URL. Jika keduanya ada, path harus sama. Sertifikat dan hostname yang tidak cocok menyebabkan koneksi gagal. Sertifikat self-signed server hanya boleh dipakai sebagai CA jika benar-benar dipercaya dan cocok dengan hostname. Simpan file key/credential dengan izin terbatas; jangan upload URL lengkap atau isi `.env` ke repository.

`POSTGRES_SSL=false` atau URL `sslmode=disable` **secara eksplisit menonaktifkan TLS** dan hanya layak pada lingkungan lokal/terpercaya, bukan koneksi publik. Konfigurasi yang bertentangan, `sslmode=no-verify`, `sslmode=prefer`, `uselibpqcompat`, duplikat parameter TLS, dan `sslcert`/`sslkey` (mTLS belum didukung) ditolak daripada diam-diam melemahkan keamanan. Ini perubahan kompatibilitas: provider yang sebelumnya mengandalkan sertifikat tak tepercaya atau opsi insecure akan gagal sampai CA dan hostname dikonfigurasi dengan benar. Jangan memakai `NODE_TLS_REJECT_UNAUTHORIZED=0` untuk mengatasi kegagalan TLS.

Tes mencakup PostgreSQL 17 lokal dengan sertifikat self-signed: CA yang tidak dipercaya dan hostname/IP yang salah ditolak, CA yang benar dan hostname yang sesuai berhasil, serta skrip migrasi memakai aturan yang sama. Layanan database dan CA Wispbyte/provider pengguna belum diuji. **Backup menggunakan `pg_dump`/libpq, bukan konfigurasi TLS Node ini**; ia menerapkan kebijakan TLS dan sertifikat CA tersendiri seperti dijelaskan di bawah. Restore produksi diblokir; latihan restore terbatas ke target uji yang disiapkan terpisah.

Tes TLS nyata bersifat opt-in: selain `ZENTIX_TEST_PG_SOCKET=/tmp/zentix-local-pg`, set `ZENTIX_TEST_PG_TLS=1` hanya ketika PostgreSQL disposable lokal pada port 55432 telah dikonfigurasi dengan sertifikat localhost di `/tmp/zentix-postgres-tls/server.crt` dan key privatnya. Variabel ini tidak boleh diarahkan ke database produksi. Tanpa flag TLS, tes TLS integrasi dilewati, bukan diasumsikan lulus.


## Health dan readiness

`/health` adalah pemeriksaan **liveness proses**, bukan tes koneksi langsung. Field `database.connected` hanya status backend yang diketahui proses dan `liveCheck:false` menegaskan bahwa ia tidak membuktikan PostgreSQL sedang dapat dijangkau. Jangan gunakan `/health` sebagai bukti data tersimpan.

`/ready` memerlukan Discord siap dan menjalankan `SELECT 1` pada pool PostgreSQL untuk setiap pemeriksaan; jika gagal atau melewati batas 2 detik, HTTP 503 tanpa rincian error privat. Probe yang sedang menggantung dibagi bersama agar banyak permintaan tidak menumpuk query; jika query benar-benar tidak pernah selesai, readiness tetap gagal sampai driver menyelesaikannya atau proses direstart. Pool kembali normal setelah gangguan sementara akan menghasilkan 200 lagi ketika pemeriksaan selanjutnya berhasil. Ini hanya snapshot kondisi saat diperiksa: ia tidak menjamin koneksi tetap sehat untuk perintah berikutnya, tidak otomatis mematikan bot, tidak menghentikan interaksi Discord, dan tidak memvalidasi seluruh tabel/skema, data, TLS atau backup. Status versi skema yang ditampilkan adalah versi yang diharapkan aplikasi, bukan pemeriksaan ulang ke database.

Tes lokal mencakup HTTP 503/200, timeout, 100 permintaan bersamaan dan pemutusan serta pemulihan jalur socket ke PostgreSQL 17 disposable. Lingkungan Wispbyte dan perilaku panelnya terhadap 503 belum diuji. Pencegahan perubahan atau respons keliru pada tiap fitur ketika database terputus masih perlu audit tersendiri.


## Backup PostgreSQL dan status restore

`npm run backup:db` membuat archive `pg_dump` format custom ke `BACKUP_DIR` (default `./backups`) dengan file baru mode 0600 dan nama acak. `-- --output <path>` dapat memilih nama spesifik; file yang sudah ada dan symlink pada komponen terakhir ditolak. Direktori baru dibuat 0700, tetapi izin direktori yang sudah ada tidak diubah dan semua direktori induk **harus tepercaya**: perlindungan ini bukan race-free jika pihak lain dapat mengganti path. Pastikan path berada pada penyimpanan persisten, hak akses tepat, dan backup disalin secara aman ke lokasi terpisah. Backup dapat mengandung seluruh data sensitif; batasi akses dan atur enkripsi/retensi secara operasional.

Untuk backup lewat TLS, berikan CA tepercaya melalui `POSTGRES_SSL_CA_FILE` atau parameter `sslrootcert` pada URL; libpq dipaksa `verify-full`, termasuk ketika URL memakai `require`/`verify-ca`. Berbeda dengan runtime Node yang bisa memakai CA sistem, backup saat ini **mewajibkan path CA eksplisit** ketika TLS aktif. Parameter URL selain `host`, `port`, `sslmode`, dan `sslrootcert`, nama database di luar subset ASCII aman, TLS tidak tepercaya dan konfigurasi bertentangan ditolak. `POSTGRES_SSL=false` atau `sslmode=disable` mematikan TLS dan hanya untuk jaringan lokal tepercaya. `pg_dump` dan `pg_restore` harus tersedia dan versinya kompatibel dengan server PostgreSQL.

Password dan URL lengkap tidak ditaruh pada argumen proses anak atau log; password tetap disampaikan kepada `pg_dump` melalui environment (`PGPASSWORD`), yang dapat dibaca oleh proses berprivilege atau pengguna OS yang sama. Output error `pg_dump` tidak dicetak untuk menghindari kebocoran rahasia; perbaiki konfigurasi secara aman bila gagal. `pg_restore --list` hanya memeriksa bahwa daftar archive dapat dibaca, **bukan** bukti semua data bisa dipulihkan. Backup yang gagal dibersihkan, dan tidak ada penghapusan otomatis backup lama: `BACKUP_RETENTION_DAYS`/`--retention-days` tidak lagi menghapus file, `--retention-days` sekarang ditolak. Kelola retensi secara sadar.

`npm run restore:db` tetap **dinonaktifkan**, termasuk dengan flag konfirmasi. Restore produksi yang menimpa database belum diimplementasikan. Versi lama dapat menghapus/mengganti database yang salah dan mengekspos URL; jangan menggunakannya.

### Latihan restore pada database uji terpisah

`npm run backup:drill -- --input <file.dump> --confirm-db <nama_database_uji>` mengembalikan **archive terpercaya** hanya ke target yang disiapkan operator, tanpa membuat atau menghapus database. Atur `POSTGRES_RESTORE_URL` secara privat di environment, bukan di argumen CLI. Tidak ada fallback ke URL produksi. Nama target harus `zentix_restore_test_` diikuti huruf kecil, angka atau underscore, dan harus sama persis dengan `--confirm-db`. Gunakan database disposable **di server/akun terpisah dengan kredensial berizin minimal**, tanpa bot atau penulis lain; nama saja tidak membuktikan isolasi. JANGAN mengarahkannya ke produksi, walaupun namanya memenuhi syarat.

Skrip memeriksa beberapa objek user umum sebelum restore dan menolak target yang tidak kosong. Pemeriksaan tersebut **bukan jaminan database benar-benar kosong**, bukan mekanisme penguncian terhadap penulis lain dan tidak mendeteksi semua objek/konfigurasi global. `pg_restore` tidak memakai `--clean`, memakai `--exit-on-error --single-transaction`, dan akan rollback jika SQL gagal sebelum commit. Saat timeout atau koneksi terputus, hasil commit bisa tidak diketahui: periksa target sebelum mencoba lagi. Archive dapat menjalankan SQL arbitrer; gunakan hanya backup yang dipercaya. Terapkan TLS/CA libpq dan pembatasan URL yang sama dengan backup. Detail error child disembunyikan untuk mengurangi kebocoran kredensial. Pengujian lokal mencakup restore dengan data, penolakan target terisi, dan rollback ketika objek dependency hilang. Keberhasilan hanya berarti restore SQL selesai; bandingkan isi dan uji fungsi aplikasi secara terpisah. Jangan menyimpan file dump di tempat tidak aman. Alur restore produksi, penyimpanan offsite dan tes pada Wispbyte masih perlu diselesaikan.

Tes menggunakan PostgreSQL 17 lokal mencakup dump dengan isi data dan restore ke database disposable, file 0600, penolakan overwrite/symlink, kegagalan dump tanpa sisa file parsial, redaksi rahasia, serta TLS CA dan hostname. Hasil lokal tidak menjamin izin atau kelengkapan backup provider lain; `pg_dump` tidak otomatis membackup semua role global dan konfigurasi server PostgreSQL.


## Pengamanan runtime tiket (parsial)

Pembacaan data tiket, jumlah tiket terbuka, dan statistik PostgreSQL kini meneruskan error saat database tidak tersedia, bukan menganggap tiket tidak ada atau jumlah nol. Penghapusan melalui facade tiket dan `deleteFromDb` tidak lagi melaporkan sukses bila backend mengembalikan false. Nomor tiket PostgreSQL dialokasikan dengan transaksi dan row lock pada counter yang sama (`temp_data`), bukan baca–ubah–tulis; nilai tidak valid atau memiliki TTL ditolak tanpa direset. Tes PostgreSQL lokal mencakup 100 alokasi bersamaan, counter lama, data rusak dan error akses. Alokasi dilakukan sebelum pembuatan kategori/channel Discord, sehingga kegagalan counter tidak membuat kategori baru; nomor bisa terlewati jika langkah Discord berikutnya gagal.

Ini **belum** membuat sistem tiket sepenuhnya aman: pemeriksaan batas tiket per pengguna dan pembuatan channel bukan transaksi lintas Discord/PostgreSQL, sehingga permintaan bersamaan masih bisa melewati batas, dan hasil commit yang tak diketahui dapat meninggalkan nomor terpakai. Penyimpanan/edit tiket serta efek samping Discord perlu audit dan rekonsiliasi lebih lanjut. Jalur database lain masih dapat mengembalikan default saat gagal. Belum diuji pada Discord atau hosting sesungguhnya.


## Moderasi warning dan `/wipedata`

Operasi warning PostgreSQL membaca record langsung dan gagal tertutup jika database tidak dapat diakses, record rusak, memiliki TTL, atau versi canonical dan legacy sama-sama ada. Data rusak **tidak di-reset otomatis**. Tambah/hapus/clear memakai transaksi dan advisory transaction lock per guild/pengguna, dengan sequence ID persisten. Facade PostgreSQL menolak penulisan/penghapusan langsung untuk key warning dan sequence agar jalur ini tidak terlewati oleh kode bot yang menggunakan facade tersebut. Tes lokal 100 penambahan paralel menghasilkan 100 warning dan ID unik; perubahan lewat SQL langsung, skrip eksternal, kode lama/instans versi lama, dan operasi efek Discord tidak otomatis mengikuti lock. Jangan jalankan versi lama dan baru bersamaan. Tidak ada jaminan terhadap hasil commit yang tidak diketahui saat koneksi terputus: periksa data sebelum mengulang.

Migrasi key tidak lagi menghapus key legacy hanya karena canonical sudah ada; kedua record dipertahankan untuk rekonsiliasi. Untuk rename key berbasis `temp_data`, penghapusan legacy dilakukan hanya jika insert canonical benar-benar berhasil. Migrasi key tidak lagi berjalan otomatis saat startup. Pemeriksaan read-only akan menghentikan startup jika mendeteksi key legacy, meskipun marker migrasi lama ada. Migrasi manual masih memiliki jalur yang bukan transaksi penuh; gunakan hanya untuk data yang sudah ditinjau saat semua bot/penulis berhenti dan setelah backup terverifikasi. Perubahan ini tidak memulihkan key yang sebelumnya telah dihapus. Pemeriksaan konflik warning mungkin memblokir fitur sampai operator merekonsiliasi data secara hati-hati.

`/wipedata` dan tombol konfirmasi lama kini **dinonaktifkan untuk semua backend**: implementasi lama bisa menghapus sebagian data namun mengklaim semua terhapus. Tidak ada data yang dihapus oleh perintah tersebut. Pengguna yang ingin meminta penghapusan harus menghubungi administrator; operator perlu memeriksa semua penyimpanan, backup dan retensi secara terpisah. Ini bukan pengganti prosedur penghapusan yang telah diverifikasi.


## Pemeriksaan key legacy saat startup

Startup tidak lagi menjalankan migrasi key otomatis. Sebagai gantinya, ia memeriksa nama key `temp_data` dalam snapshot read-only; key yang cocok dengan pola legacy yang dikenal menghasilkan `LEGACY_KEYS_REQUIRE_REVIEW`, dan lebih dari 50.000 key menghasilkan `LEGACY_KEY_AUDIT_LIMIT`. Kesalahan query juga menghentikan startup. Pemeriksaan ini berjalan meskipun marker migrasi lama ada dan tidak bisa dilewati dengan `AUTO_MIGRATE=false`; `AUTO_MIGRATE` masih mengatur bootstrap ledger skema tetapi tidak lagi mengaktifkan migrasi key. Database kosong tetap bisa memulai. Startup masih dapat membuat tabel dan objek skema sebelum pemeriksaan tersebut; ini bukan startup seluruhnya read-only. Bootstrap ledger hanya boleh untuk skema tanpa tabel bot yang dikenal; database lama perlu audit/migrasi skema secara terpisah sebelum menjalankan bot.

Untuk database yang sudah berisi data lama, **jangan hapus key hanya agar bot bisa online**. Hentikan semua penulis, buat dan verifikasi backup, lalu inventarisasi dan rekonsiliasi setiap konflik terlebih dahulu. `npm run migrate:keys:dry` adalah alat preview yang ada, bukan bukti aman atau lengkap; skrip manual `npm run migrate:keys` belum menjadi migrasi end-to-end yang sepenuhnya transaksional dan belum diuji pada Neon. Jika ada error atau konflik, skrip kini mengembalikan exit code bukan nol dan tidak memperbarui marker; marker lama mungkin tetap ada. Pemeriksaan ini hanya untuk pola legacy yang dikenal dalam `temp_data`, bukan validasi semua data atau semua penulis. Perubahan setelah snapshot, instans lama, skrip lain dan akses SQL langsung tetap perlu dikoordinasikan. Jika batas audit terlampaui, tinjau secara offline; jangan menghapus data sebagai jalan pintas.

Tes PostgreSQL lokal mencakup database baru, marker lama plus key legacy, pembatasan scan dan penolakan startup tanpa mengubah record key; tidak ada Neon atau Wispbyte yang digunakan.


## Pemeriksaan skema sebelum bootstrap

Sebelum DDL, startup memeriksa objek di `current_schema()`. Bila tabel bot yang dikenal sudah ada tetapi ledger `schema_migrations` kosong/tidak ada, startup berhenti dengan `SCHEMA_UNVERSIONED_EXISTING`, bukan mencatat versi seolah-olah database baru. Bila ledger versinya benar tetapi tabel bot yang diharapkan tidak lengkap atau bukan tabel biasa, startup berhenti dengan `SCHEMA_INCOMPLETE`. Versi berbeda tetap ditolak. Database tanpa tabel bot dapat di-bootstrap sesuai `AUTO_MIGRATE`; jika bootstrap gagal setelah sebagian tabel dibuat, startup berikutnya akan menolak skema parsial dan memerlukan peninjauan offline, bukan menghapus atau memperbaikinya diam-diam.

`npm run migrate` juga memeriksa kondisi ini sebelum melakukan DDL dan tidak otomatis meng-upgrade skema lama. `migrate:status` dan `migrate:check` tidak lagi membuat ledger saat hanya membaca status. Ledger menggunakan nama tetap `schema_migrations`. Hentikan semua bot dan penulis lain selama bootstrap atau migrasi. Pemeriksaan ini bukan kunci global, tidak menutup race ketika beberapa proses memulai bersamaan, dan tidak memeriksa kolom, constraint, data, ekstensi, indeks atau trigger secara menyeluruh. Nomor versi yang cocok bukan bukti bahwa seluruh skema valid. Error indeks/trigger runtime masih bisa hanya dicatat lalu dilanjutkan.

Tes PostgreSQL 17 lokal mencakup skema kosong, tabel lama tanpa ledger (data tetap utuh), ledger versi benar dengan tabel yang hilang, dan penolakan oleh skrip migrasi sebelum DDL. Neon, izin provider dan Wispbyte belum diuji.


## Risiko runtime konfigurasi server

Saat pembacaan konfigurasi guild gagal, sebagian jalur masih mengembalikan konfigurasi default. Jika database kemudian pulih sebelum penulisan, perubahan pengaturan dapat menimpa konfigurasi yang sebenarnya dengan default; perubahan bersamaan juga dapat saling menimpa. Jangan ubah pengaturan saat database tidak stabil atau dari beberapa penulis sekaligus. Ini belum diperbaiki dan tes `/ready` tidak menjamin keselamatan semua perintah. Simpan backup dan uji pemulihan di lingkungan terpisah.
